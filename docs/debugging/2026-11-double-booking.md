# Справа: подвійні бронювання (листопад 2026)

**Симптом.** Диспетчерка повідомила про три випадки за жовтень: дві групи
в одній аудиторії в той самий час. Запит `scripts/debug/overlaps.sql` знайшов
чотири пари перетинних активних бронювань.

**Гіпотези.** Г1 – кеш доступності; Г2 – часові пояси; Г3 – подвійне надсилання
форми; Г4 – гонка «перевір, потім дій» у `createBooking()`.

**Відтворення.** `pnpm tsx scripts/debug/double-booking.ts --rounds 20 --concurrency 40`:
дублікати в більшості раундів; з `--concurrency 1` – жодного.

**Докази.** Журнал запитів PostgreSQL (`log_statement=all`, `log_timezone=UTC`):
обидва процеси виконують SELECT перевірки до будь-якого INSERT.

**Відкинуті виправлення.**
1. Інтерактивна транзакція Prisma: на READ COMMITTED незафіксована вставка
   сусіда невидима для SELECT – дублікати лишаються.
2. Блокування в пам'яті процесу: зелено на одному екземплярі, але продакшн –
   два контейнери за балансувальником.

**Причина.** Правило «аудиторія не зайнята двічі одночасно» існувало лише
в коді застосунку; база, яка бачить усі паралельні запити, про нього не знала.

**Виправлення.** Обмеження `booking_no_overlap`: `EXCLUDE USING gist ("roomId" WITH =,
tstzrange("startsAt", "endsAt", '[)') WITH &&) WHERE ("cancelledAt" IS NULL)`
(міграція `20261104090000_booking_no_overlap`, розширення `btree_gist`);
23P01 → 409 `ConflictError` (`isOverlapViolation`); серії – в одній транзакції.

**Регресія.** `apps/api/test/booking.race.int.test.ts` (хук `afterConflictCheck`
робить гонку детермінованою): без міграції падає в першому раунді, з міграцією – 25/25.

**Перед продакшеном.** Наявні пари з `overlaps.sql` розв'язує диспетчерка;
міграцію застосовують після цього.
